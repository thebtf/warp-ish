# warp-ish — контракт проекта

## Продукт и требования

warp-ish — локальный терминал на основе официального Warp. Текущие сборки, поставка и обязательная приёмка ограничены Windows 11 x64. Поддержка macOS/Linux относится к отдельному будущему решению. Требования и архитектурные решения находятся в [DESIGN.md](docs/warp-ish/DESIGN.md).

Продукт переиспользует терминальный движок, ConPTY, рендерер, блоки, ввод, окна, вкладки, панели и локальное сохранение состояния. Встроенные AI, облако, Drive, аккаунты, синхронизация, биллинг, шаринг и телеметрия подлежат удалению из поставляемого приложения вместе с зависимыми настройками, действиями и фоновыми службами.

Работающий Warp служит исходной реализацией терминала. Проверки GUI/ConPTY подтверждают сохранение поведения после наших изменений. Объём проверки конкретного патча определяется затронутым поведением, применимый к версии набор выполняется на готовом пакете по `ACCEPTANCE.md`.

OMP и другие CLI-программы работают внутри терминала как внешние процессы. Их конфигурация, модели, роли и сессии принадлежат соответствующим программам. Собственный каталог данных warp-ish содержит только состояние терминала.

## Доменные инварианты

- Для каждой панели хранится последний известный каталог и параметры оболочки. Восстановление читает согласованный локальный снимок. Неизвестный каталог при раннем запуске сохраняет предыдущее известное значение.
- После восстановления открываются свежие оболочки в сохранённых каталогах. Повторное исполнение последней команды требует отдельного пользовательского действия.
- Удаление одного каталога обрабатывается для соответствующей панели и сохраняет восстановление остальных.
- Состав UI, реестра действий, горячих клавиш, настроек, фоновых служб и релизных зависимостей соответствует одному продуктовому контракту.
- Сеть дочерних пользовательских программ и обращения самого терминала проверяются по инициатору.
- Автоматическое обновление проверяет пригодность нового пакета до его продвижения. При включённом пользователем автообновлении пакет устанавливается при следующем обычном запуске приложения либо после явного подтверждения перезапуска.
- Настройки, история, конфигурация оболочек и раскладка сохраняются при обновлении. Миграции используют резервную копию и проверяемое восстановление последней рабочей версии.

## Исходники и сопровождение

История форка происходит из `warpdotdev/warp`. Происхождение, исходный SHA и подход к обновлениям описаны в [UPSTREAM.md](docs/warp-ish/UPSTREAM.md).

Общие терминальные типы следует отделять по назначению. Имя файла или совпадение слова AI само по себе не определяет назначение кода.

Для изменяемых терминальных моделей проверить существующую цепочку блокировок. Повторное получение того же `TerminalModel` lock в стеке вызовов может заморозить UI. Этот риск отмечен в инженерном руководстве исходной ревизии Warp.

## Сборка и проверки

При первой сборке и изменениях toolchain прочитать [руководство по сборке](docs/warp-ish/BUILD.md). Версии инструментов брать из `rust-toolchain.toml`, `Cargo.lock` и профильных скриптов текущей ревизии.

Перед изменением поведения сверить применимые сценарии в [ACCEPTANCE.md](docs/warp-ish/ACCEPTANCE.md). Проверка документации включает ссылки и `git diff --check`. Проверки кода выбираются по затронутым компонентам и поставляемому поведению.

`script/bootstrap` и `script/run` исходного Warp могут устанавливать общие агентские навыки. Подготовка зависимостей для этого проекта использует режим пропуска common skills. Проверка пакета выполняется с каталогом данных warp-ish.

## Вход в текущую работу

Если в локальной копии есть `.agent/START.md`, прочитать его для контекста текущих задач и проверок. Этот контракт хранит устойчивые требования продукта.
