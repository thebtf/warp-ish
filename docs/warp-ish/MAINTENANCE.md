# Локальное сопровождение warp-ish

`script/warp-ish/maintain.py` работает с Python 3.11+ и Git. Зависимости Python входят в стандартную библиотеку. Политика лежит рядом в `terminal-policy.json` и закреплена за upstream-коммитом `75f8808a1c94ee54840f517cfff54595589c32a5`.

## Аудит исходников

Из корня репозитория выполняется команда

```powershell
python script/warp-ish/maintain.py audit --repo .
```

В stdout поступает JSON с текущим HEAD, состоянием checkout, SHA256 прочитанных файлов, dependency seeds, default features и регистрациями подсистем. В Git используется `GIT_OPTIONAL_LOCKS=0`.

Проверяются семь конкретных файлов.

- `Cargo.toml`
- `app/Cargo.toml`
- `crates/warp_terminal/Cargo.toml`
- `app/src/lib.rs`
- `app/src/app_state.rs`
- `app/src/settings/init.rs`
- `app/src/root_view.rs`

Проверка Cargo учитывает workspace inheritance, package aliases, известные локальные пути, target/build/dev/optional dependencies, определения features и их рёбра. Политика хранит наблюдения об исходной ревизии и список запрещённых флагов. Изменённая зависимость и новое имя feature попадают в `scope_and_drift` для разбора.

Подтверждённые изменения Windows-зависимостей и локальной навигации записываются в `reviewed_terminal_drift`. Для зависимостей учитывается хеш точного разрешённого объявления. Имена регистраций остаются привязаны к файлу и категории. Запрещённые зависимости и регистрации проверяются независимо от этих записей. `shell_widget_handoff` сохраняет передачу клавиш оболочке для fzf и atuin.

Необязательное поле политики `forbidden_source_paths` задаёт точные пути относительно корня репозитория и причины исключения. Проверка `source_paths` выявляет любой существующий entry (файл, каталог или symlink, включая dangling link), даже без Cargo dependency edge. Она читает только метаданные перечисленных путей, без рекурсивного обхода и чтения содержимого. Пути с traversal/абсолютными или неоднозначными Windows-формами отклоняются; symlink/reparse-point в родительском пути не проходится. Ошибка проверки даёт `unverified`, а обнаруженный исходник — `fail` для audit, scoped removal и candidate. Отсутствующее поле совместимо со старой политикой. Этот результат покрывает только перечисленные пути; отсутствие findings не подтверждает полное удаление платформы и не заменяет runtime acceptance. Существующая `forbidden_paths` по-прежнему классифицирует только зависимости Cargo.

Проверка Rust маскирует комментарии и строковые литералы, нормализует raw identifiers и сохраняет номера строк. Известные вызовы `init`, регистрации settings, account/cloud factories и поля persisted session дают адресные findings. Новые module/init/service/public-field names попадают в `scope_and_drift`. Различие LF/CRLF отражается в файловом SHA256. Семантический drift вычисляется из разобранных TOML и имён в исходниках.

У штатного Warp ожидается `scoped_removal.status = fail`. Проверка компиляции и native terminal runtime отражается отдельно в `terminal_baseline`. Полный `terminal_only` остаётся `unverified`, когда перечисленные статические проверки проходят. Внешняя проверка должна охватить остальные crates, generated/macro registrations, настройки, процессы, сетевые обращения самого приложения и пользовательские terminal-сценарии.

## Наблюдение upstream

```powershell
python script/warp-ish/maintain.py observe-upstream `
  --repo D:\Dev\warp-ish `
  --base f7fc2f2a08a3aa446baa23960710e630c5defd6e `
  --remote upstream `
  --timeout 30 `
  --state D:\Dev\warp-ish\.agent\runs\upstream\latest.json
```

Команда читает `git ls-remote --symref` для HEAD, main, master и tags. Отчёт содержит symbolic HEAD, SHA веток, tag object SHA, dereferenced target SHA и сравнение HEAD с закреплённой базой. `head_equal_to_base = false` обозначает разные SHA. Проверке ancestry нужны локальные объекты истории.

`stable_tags` выделяется по закреплённому regexp для формата Warp `v0.2026.06.03.09.49.stable_00` и stable SemVer. Все tags сохраняются в `tags`. Назначение и порядок релизов проверяются отдельно от совпадения имени с шаблоном.

Успешное наблюдение атомарно заменяет `--state`. Ошибка сети, timeout или ошибка Git возвращает `status = unverified` в stdout. Предыдущее успешное наблюдение сохраняется. Время свежести берётся из `observed_at` внутри файла. Состояние задачи планировщика и текущий exit code дополняют last-good JSON.

Для фонового запуска используются закрытый stdin, `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, пустой `core.askPass` и `credential.interactive=false`. Обработчики из переменных `GIT_ASKPASS` и `SSH_ASKPASS` удаляются из окружения дочернего Git. Timeout допускает значения от 1 до 60 секунд.

Для Task Scheduler подготовлен `script/warp-ish/install-upstream-observer.ps1`. Он закрепляет полный путь Python и каталог проекта, выбирает текущего пользователя с обычными правами и задаёт ежедневное время по часовому поясу Windows. По умолчанию используется 04:00. Выполнение требует входа пользователя в Windows. Задача получает лимит три минуты и `StartWhenAvailable`, повторный параллельный запуск пропускается.

```powershell
.\script\warp-ish\install-upstream-observer.ps1 -Repo D:\Dev\warp-ish -Python D:\Bin\miniconda3\python.exe -Time 04:00
Get-ScheduledTaskInfo -TaskName warp-ish-upstream-observer
```

Установщик проверяет принадлежность существующей задачи проекту и повторно возвращает `Unchanged` при совпадении настроек. Для удаления своей задачи используется `-Remove` с тем же `-Repo`. JSON последнего наблюдения сохраняется. Первое фактическое выполнение и проверенные параметры задачи записаны в [FOUNDATION.md](FOUNDATION.md).

Время `observed_at` и `LastTaskResult` проверяются вместе. Файл хранит последнее успешное наблюдение, а планировщик показывает исход последней попытки. Для подробной диагностики команду `observe-upstream` можно повторить вручную с сохранением stdout и stderr в каталог конкретного прогона.

## Подготовка кандидата

Для воспроизводимого переноса нужны три полных SHA коммитов и отдельная рабочая копия задачи nvmd-ai. Исходная копия должна быть чистой. `--fork` должен совпадать с её HEAD. `--base` должен быть предком обоих `--fork` и `--target`. Целевая ревизия должна быть доступна локально.

Открой копию согласованной задачи от точного SHA цели. Для новой задачи, прошедшей пересказ, используй `nvmd-ai-client task start <ID> --base <SHA>`. Для продолжения используй `nvmd-ai-client wt open <ID> --base <SHA>` и проверь HEAD существующей копии.

```powershell
$source = git rev-parse --show-toplevel
$baseSha = 'f7fc2f2a08a3aa446baa23960710e630c5defd6e'
$forkSha = git rev-parse HEAD
$targetSha = git rev-parse upstream/master
nvmd-ai-client task start $replayTaskId --base $targetSha
# $candidateWorktree — путь, напечатанный клиентом при открытии.
python script/warp-ish/maintain.py candidate `
  --repo $source `
  --base $baseSha `
  --fork $forkSha `
  --target $targetSha `
  --worktree $candidateWorktree
```

Перед применением патча команда проверяет регистрацию целевой копии в том же репозитории, путь `.work/wt/<ID>`, ветку `task/<ID>`, чистый индекс и совпадение HEAD с `--target`. Копию открывает клиент nvmd-ai с обычными настройками Git.

Git вычисляет полный binary diff `base → fork`, включая исходные идентификаторы blob. Команда записывает SHA256 и применяет патч через `git apply --index --3way`. Итоговое дерево закрепляется `git write-tree` и возвращается как `pins.candidate_tree`. HEAD целевой копии остаётся на ревизии апстрима. Отчёт содержит состояние исходной копии до и после переноса и поле `main_guard`.

Для повторного воспроизведения открой копию другой задачи от того же `--target` и передай `--expected-tree` из предыдущего отчёта. Несовпадение дерева завершает подготовку с `fail`. При конфликте копия сохраняется с индексом конфликта и списком `conflicts`.

`preparation.status = pass` означает, что патч применён. Вложенный `audit` оценивает наличие удаляемых подсистем. Кандидат с успешно применённым патчем и сохранённым агентским или облачным кодом получает общий `status = fail`. LFS hydration, нативная сборка и проверка готового пакета выполняются отдельно.

## JSON contract v1

Раздел ниже описывает уже реализованные команды. Полный цикл сопровождения задан отдельным разделом в конце документа.

Общие поля отчёта соответствуют следующей базовой JSON Schema. Остальные поля зависят от команды.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["schema_version", "command", "status"],
  "properties": {
    "schema_version": {"const": 1},
    "command": {"enum": ["audit", "candidate", "observe-upstream"]},
    "status": {"enum": ["pass", "fail", "unverified"]},
    "error": {"type": "string"},
    "observed_at": {"type": "string", "format": "date-time"},
    "source": {"type": "object"},
    "checks": {"type": "object"},
    "inventory": {"type": "object"},
    "scoped_removal": {"$ref": "#/$defs/check"},
    "terminal_baseline": {"$ref": "#/$defs/check"},
    "terminal_only": {"$ref": "#/$defs/check"},
    "preparation": {"$ref": "#/$defs/check"},
    "main_guard": {"$ref": "#/$defs/check"},
    "audit": {"type": "object"},
    "pins": {"type": "object"},
    "head": {"type": "object"},
    "branches": {"type": "object"},
    "tags": {"type": "array"},
    "stable_tags": {"type": "array"},
    "comparison": {"type": "object"}
  },
  "$defs": {
    "check": {
      "type": "object",
      "required": ["status"],
      "properties": {"status": {"enum": ["pass", "fail", "unverified"]}}
    }
  }
}
```

- `audit` возвращает `source`, `policy`, `checks`, `inventory`, `scoped_removal`, `terminal_baseline`, `terminal_only`, `scope_limits`. Каждый check содержит `status` и `findings`.
- `candidate` возвращает `preparation`, `source_before`, `source_after`, `main_guard`. После успешной проверки pins добавляются `base`, `fork`, `target`, `patch_sha256`, затем `candidate_tree`. После replay появляется вложенный `audit`. Частичная подготовка дополнена `error`, при конфликте также `conflicts` и `patch_error`.
- `observe-upstream` возвращает `observed_at`, `remote`, `head`, `branches`, `tags`, `stable_tags`, `comparison`. Успешная запись state добавляет `state_path` в stdout. Сам сохранённый state содержит данные наблюдения.
- Ошибка до выполнения команды может вернуть только общие поля и `error`. Потребитель сначала проверяет `status` и наличие нужных полей.

Exit code равен `0` для `pass`, `1` для `fail`, `2` для `unverified` или ошибки CLI. Обычный аудит полностью очищенного проверяемого подмножества заканчивается кодом `2`, поскольку полная terminal-only проверка требует внешнего подтверждения. Успешный observer заканчивается кодом `0`. Код `1` кандидата может сопровождаться `preparation.status = pass` и требует чтения вложенного audit.

## Regression tests

```powershell
python -m unittest discover -s tests/warp-ish -p test_maintain.py -v
```

Тесты создают временные Git-репозитории и локальные remotes. Они покрывают SHA guards, чистоту исходного checkout, воспроизводимость tree SHA, конфликт replay, неизвестные зависимости/регистрации, комментарии и литералы Rust, варианты видимости persisted fields, CRLF, успешный observer, сетевую ошибку и timeout с сохранением last-good state. Native Windows build и взаимодействие с терминалом проверяются отдельным acceptance harness.

## Задание на автоматическое сопровождение

Реализовать локальный Windows-исполнитель поверх существующих команд. Пользовательский вход — один полный цикл уровня `update --once`, пригодный для вызова планировщиком и повторного запуска. Точное имя команды исполнитель выбирает при реализации и записывает здесь. Ежедневный observer сейчас выполняет только наблюдение.

1. Выбрать стабильный upstream target по закреплённой политике, загрузить его объекты, проверить ancestry и записать полный SHA. Сохранять обработанные ревизии и состояние незавершённого прогона. Защищать исполнение от параллельных запусков.
2. Создать отдельный кандидат и воспроизвести правила форка. Наследуемые терминальные компоненты брать из target. Для полностью исключённых компонентов поддерживать явные правила удаления, охватывающие новые файлы. Для общих типов и точек запуска применять проверяемые патчи с предусловиями. Изменение назначения или границы компонента создаёт задачу на адаптацию.
3. Проверить весь релевантный граф зависимостей, регистрации, настройки, actions, фоновые службы и состав пакета. Расширить исходный семифайловый audit по фактическому составу удаления. Совокупный Git diff сам по себе пропускает новые upstream-файлы в исключаемых подсистемах.
4. Выполнить LFS hydration, Windows-сборку, целевые тесты и приёмку фактического пакета. Сведения о запуске связывать с исходными SHA, toolchain, командами и SHA256 пакета. Порядок быстрых проверок перед тяжёлыми выбирается по стоимости и зависимостям.
5. Продвигать полностью проверенный пакет в локальный канал готовых версий. Хранить последний рабочий пакет и совместимую резервную копию данных. При включённом пользователем автообновлении применение выполняется при следующем обычном запуске приложения или подтверждённом перезапуске. Проверить восстановление после неудачного обновления или миграции.
6. При конфликте, неклассифицированном изменении или регрессии сохранять worktree, логи и задачу с `base/fork/target`, причиной остановки и критериями результата. Доставлять задачу через действующий механизм локальной платформы и проверять факт получения. Если исполнитель недоступен, задача остаётся в наблюдаемом состоянии ожидания адаптации.
7. Сопровождающий агент адаптирует кандидат, добавляет нужную регрессию и повторно запускает тот же цикл проверок. Число попыток и расход ресурсов ограничиваются записанной политикой. Изменение критериев допуска проходит отдельное review. Пользователю передаются продуктовые решения и конкретные внешние блокеры.
8. Проверить цикл на совместимом обновлении, конфликте, неизвестной регистрации, сбое проверки и повторном запуске. Добавить запрещённую службу или команду в тестовую копию и подтвердить остановку продвижения. Затем выполнить два исторических перехода по `UPSTREAM.md`.

Первый пакет допускает ручное выполнение воспроизводимых GUI-сценариев в тестовой среде с сохранением результатов. Автоматическое продвижение следующих версий требует машинно наблюдаемого результата обязательных проверок. Во время реализации отчёт сохраняет точный статус каждого шага.

История, очередь адаптаций и отчёты хранятся в каталоге `.agent/runs/` проекта с атомарным сохранением. Пакеты размещаются в `.agent/build/packages/<version>/`. Тяжёлые задания Windows выполняются отдельно от интерактивной OMP-сессии. Действующая задача `warp-ish-upstream-observer` подключается к полному циклу после его проверки. Внешняя публикация выполняется по отдельному явному указанию пользователя.
