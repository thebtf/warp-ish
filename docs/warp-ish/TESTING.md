# Проверки warp-ish

Сценарии первой поставки перечислены в [ACCEPTANCE.md](ACCEPTANCE.md). Скрипт `script/warp-ish/verify.py` покрывает предварительную проверку среды и сохранённых полей терминальной раскладки. Для запуска нужен Python 3.11 или новее, дополнительные пакеты Python не требуются.

Работающий GUI, ConPTY и терминальные функции наследуются из Warp. Проверки относятся к регрессиям после наших изменений. Сначала выполняются проверки затронутого поведения, применимый к версии набор из `ACCEPTANCE.md` выполняется на пакете Windows 11 x64. Ручной воспроизводимый сценарий с наблюдаемым результатом допустим для первого пакета. Автоматическое продвижение обновлений требует машинно наблюдаемых результатов обязательных сценариев.

## Статус результатов

Каждая команда пишет JSON с областью проверки `scope`, результатом `status` и отдельными `checks`. Поле `runtime_acceptance` сохраняет `NOT_RUN` до наблюдаемого выполнения Windows-сценариев в построенном приложении. Результат сравнения SQLite подтверждает равенство выбранных сохранённых полей. Реальный каталог запущенной оболочки проверяется через `Get-Location` после восстановления.

`NOT_RUN` обозначает запланированную проверку, которую выполняют по готовности соответствующего кода или пакета. Обнаруженные дефекты сопровождаются воспроизводимым сценарием и фактическим результатом. Исходные прогоны из `FOUNDATION.md` используются как подтверждённая база для начала изменений.

Коды завершения скрипта

- `0` — все проверки указанной области прошли.
- `1` — проверка завершилась ошибкой.
- `2` — неверные аргументы командной строки.
- `3` — часть проверок указанной области ещё не выполнена.

Отчёты и логи отдельных прогонов помещаются в `.agent/runs/<run-id>/`. В JSON-снимках присутствуют пути и названия тестовых вкладок. Для fixture используются созданные специально для проверки данные.

## Среда сборки

Из корня репозитория в PowerShell

```powershell
python script/warp-ish/verify.py preflight --repo . --report .agent/runs/local/preflight.json
$LASTEXITCODE
```

Preflight проверяет корень Git, наличие исходного апстримного коммита в истории, доступность закреплённых `rustc` и Cargo, Git LFS, CMake, Clang, MSVC x64, заголовков и библиотек Windows SDK. Он также записывает SHA текущего HEAD, количество изменений рабочего дерева, версию Python и свободное место. Все subprocess probes получают `RUSTUP_AUTO_INSTALL=0` и `GIT_OPTIONAL_LOCKS=0`. Загрузка toolchain и LFS вынесена в отдельный явный шаг онбординга.

Порог свободного места можно задать параметром `--min-free-gib`. Без него отчёт фиксирует измеренное свободное место. Потребность полной сборки в диске и памяти требуется измерить первым реальным прогоном. Наличие инструментов ещё требует проверки компиляцией, поле `build_status` остаётся `NOT_RUN`.

Проверка LFS обнаруживает оставшиеся pointer-файлы и отсутствующие рабочие файлы. Поле `content_hashes_verified` отражает, что полное хеширование LFS-объектов выполняется отдельной проверкой целостности. На Linux/MSVC-недоступном окружении Windows-проверка получает `NOT_RUN`, итоговый код команды равен `3`, если остальные проверки прошли.

## Fixture-тесты инструмента

```powershell
python -m unittest discover -s tests/warp-ish -p test_verify.py -v
$LASTEXITCODE
```

Тесты создают временную SQLite-базу с двумя окнами, тремя вкладками, разделённой панелью, Unicode-каталогом и путём с пробелами. Затем выполняются backup SQLite, чтение и сравнение. Смена числовых идентификаторов строк допустима, поскольку upstream пересоздаёт их при сохранении состояния. Изменение CWD, направления разделения и активной вкладки обнаруживается.

Дополнительные случаи проверяют `NULL` и пустой CWD, пропавшую панель, повтор UUID, неверный родительский узел, переход между вкладками, несовместимую схему, повреждённый JSON и попытку записать результат поверх входной базы. Проверяются типы флагов, конечность координат и размеров, согласованное отсутствие геометрии, неотрицательный flex и значения состояния окна. Допустимы полностью отсутствующая геометрия, отрицательная координата монитора, нулевой flex и `NULL` flex. Fixture использует сокращённую схему читаемых колонок. Миграции Rust-приложения и код восстановления Warp требуют собственного запуска.

## Терминальные Rust-тесты без GUI

На закреплённом upstream доступны два набора in-memory тестов библиотеки `warp_terminal`. Они используют общий тестовый бинарник. Первый компилируемый прогон требует dev dependencies и линковки MSVC. После заполнения кэша повторение возможно с `--offline`.

```powershell
$env:RUSTUP_AUTO_INSTALL = '0'
$env:CARGO_TARGET_DIR = Join-Path $PWD '.agent/build/baseline'
cargo test -p warp_terminal --lib --locked --offline -j 2 'model::ansi::tests::' -- --test-threads=1
cargo test -p warp_terminal --lib --locked --offline -j 2 'model::grid::flat_storage::tests::' -- --test-threads=1
```

ANSI-набор проверяет разбор CSI/SGR, цветов, OSC 8 links, OSC 7 CWD, DCS shell integration и Windows drive-letter paths. В этом pin на Windows ожидаются 79 выполняемых тестов. Набор FlatStorage проверяет Unicode width, стили, round-trip строк, scrollback и resize. В нём ожидаются 10 выполняемых тестов и один upstream ignored complex-emoji case. Проверять число выполненных тестов в итоговой строке каждого запуска. [ANSI tests](https://github.com/warpdotdev/warp/blob/f7fc2f2a08a3aa446baa23960710e630c5defd6e/crates/warp_terminal/src/model/ansi/mod_tests.rs) · [FlatStorage tests](https://github.com/warpdotdev/warp/blob/f7fc2f2a08a3aa446baa23960710e630c5defd6e/crates/warp_terminal/src/model/grid/flat_storage/mod_tests.rs)

Результаты этих прогонов подтверждают выбранную логику парсера и хранения строк. Сценарии GUI, ConPTY и реального каталога восстановленной оболочки выполняются отдельно.

## Снимки реальной раскладки

Для каждого сценария используй отдельный тестовый профиль. Перед миграцией сохрани базу профиля командой `backup-database`. Она открывает источник в режиме чтения и создаёт проверенную самостоятельную копию через SQLite Backup API, включая зафиксированные изменения в WAL. Каталог назначения должен уже существовать, а имя снимка должно быть свободно. Простое копирование основного файла при активном WAL может потерять последние изменения. SQLite может создать служебные файлы WAL/SHM рядом с источником в рамках штатной работы режима чтения.

`capture-layout` читает самостоятельную копию с `mode=ro&immutable=1`. Перед чтением она отклоняет вход с соседними `-wal`, `-shm` или `-journal` и проверяет целостность SQLite, ссылки и неизменность хеша во время чтения.

```powershell
python script/warp-ish/verify.py backup-database --source (Join-Path $fixtureData 'warp.sqlite') --snapshot .agent/runs/restore/before.sqlite
python script/warp-ish/verify.py capture-layout --database .agent/runs/restore/before.sqlite --snapshot .agent/runs/restore/before.json --report .agent/runs/restore/capture-before.json
python script/warp-ish/verify.py capture-layout --database .agent/runs/restore/after.sqlite --snapshot .agent/runs/restore/after.json --report .agent/runs/restore/capture-after.json
python script/warp-ish/verify.py compare-layout --before .agent/runs/restore/before.json --after .agent/runs/restore/after.json --report .agent/runs/restore/comparison.json
```

В тестовой раскладке должны присутствовать только терминальные вкладки. Проверка сравнивает сохранённую последовательность окон и вкладок, активное окно, активные вкладки, геометрию окон, split-дерево, относительные размеры, терминальные UUID, CWD, фокус и заголовки. Идентификаторы строк нормализуются по возрастанию ID. Upstream явно сортирует вкладки и дочерние панели по ID. Окна он вставляет последовательно, а читает без `ORDER BY`, поэтому сортировка окон в инструменте задаёт каноническое представление сохранённых строк. Порядок реальных GUI-окон проверяется отдельно при runtime-приёмке. Группы вкладок, панели Drive и сериализованная конфигурация оболочки выходят за текущую схему снимка. Для сохранения всей конфигурации приложения нужен отдельный контракт после отделения терминальных данных от платформенных.

Перед каждым сравнением фиксируются исходный SHA, SHA256 исполняемого файла, командная строка, каталог тестовых данных и сценарий перезапуска. После запуска в каждой панели выполняется `Get-Location`. Его вывод и привязка к панели сохраняются рядом со снимками. Для случая исчезнувшего каталога ожидаемый fallback задаётся отдельно. Такое изменение каталога требует проверки поведения оболочки.

Ограничения текущего инструмента определяют его область проверки. Для полного продуктового контракта исполнитель добавляет проверки конфигурации оболочек, настроек, истории и миграций реального хранилища. Группы вкладок проверяются, если включены в сохраняемый интерфейс. Межверсионный сценарий включает резервную копию и восстановление после отказа миграции.

## Изоляция запуска

В исследованном коммите `f7fc2f2a08a3aa446baa23960710e630c5defd6e` обработчик `WARP_DATA_PROFILE` ограничен `cfg!(debug_assertions)`. В релизной сборке этот механизм не выбирает отдельный профиль. На основании этой переменной невозможно обещать изоляцию релизного EXE. Проверены реализация профиля и построение путей. [channel/state.rs](https://github.com/warpdotdev/warp/blob/f7fc2f2a08a3aa446baa23960710e630c5defd6e/crates/warp_core/src/channel/state.rs#L140) · [paths.rs](https://github.com/warpdotdev/warp/blob/f7fc2f2a08a3aa446baa23960710e630c5defd6e/crates/warp_core/src/paths.rs)

Для запуска кандидата используются явный путь к EXE и собственные пути состояния, настроек, истории, shell integration, single-instance IPC и crash output. Приёмка релизного пакета может выполняться в выделенном Windows-пользователе или Windows VM с тестовыми данными. Исполнитель выполняет сценарии на первом готовом пакете доступными средствами, затем автоматизирует повторение для обновлений.

В Windows warp-ish явный `WARP_DATA_PROFILE` действует и в релизной сборке. Для испытания на текущей Windows задай уникальное имя профиля из строчных латинских букв, цифр и дефисов. Имя начинается с буквы или цифры и содержит до 48 символов. Профиль отделяет каталоги приложения, ключ настроек и канал запуска. Нативный PowerShell использует отдельный файл PSReadLine и пропускает пользовательские скрипты старта. Для проверок публичного локального управления укажи один и тот же отдельный `WARP_LOCAL_CONTROL_DISCOVERY_DIR` в среде GUI и клиента. Запиши в отчёте, какие данные были пустыми перед запуском.

Текущий скрипт оставляет отдельные невыполненные проверки интерактивной PowerShell/ConPTY, восстановления реального CWD после перезапуска, аварии и обновления, TUI/OMP, интерфейса и сетевого поведения. Для сетевой проверки учитываются процесс приложения и поставляемые помощники, PID пользовательской PowerShell сохраняется отдельно.
