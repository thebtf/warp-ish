# Результаты подготовки warp-ish

## Ревизия и среда

Проверка выполнена 6 ноября 2026 года на Windows x64. Рабочая ветка — `warp-ish/main`, remote — `upstream`.

Исходный Warp закреплён за `f7fc2f2a08a3aa446baa23960710e630c5defd6e`, датированным 2026-11-06. Базовые сборочные проверки начаты на onboarding-коммите `e8611a739838a179f678e5156de2cb8f493905e1`. Продуктовый код содержит платформенные функции исходного Warp. Его очистка составляет следующий этап реализации.

Для проверок установлен закреплённый Rust 1.92.0. Использованы Python 3.13.14, Git LFS 3.7.1, CMake 3.31.5, Clang 22.1.0, Protobuf 34.0, MSVC 14.44.35207 и доступные Windows SDK. Cargo выполнялся с двумя параллельными заданиями.

## Автоматика апстрима

В планировщике Windows зарегистрирована задача `\warp-ish-upstream-observer`. Время 04:00 по часовому поясу `Russian Standard Time` выбрано при подготовке проекта. Задача работает под текущим пользователем после входа в Windows, с обычными правами, `StartWhenAvailable`, лимитом три минуты и пропуском повторного параллельного запуска.

Первый запуск через Task Scheduler начался 6 ноября в 16:39:21 по Москве и завершился с `LastTaskResult = 0`. Повторная установка возвращает `Unchanged`, principal сравнивается по каноническому SID. Записано успешное наблюдение HEAD `f7fc2f2a08a3aa446baa23960710e630c5defd6e` и 61 тега. На этот момент HEAD совпал с исходным pin. [Результат запуска](../../.agent/runs/2026-11-06-foundation/scheduler-first-run.json)

Файл `.agent/runs/upstream/latest.json` хранит последнее успешное наблюдение. При диагностике используются его `observed_at` и `LastTaskResult` задачи. Установщик и команды описаны в [MAINTENANCE.md](MAINTENANCE.md).

`maintain.py candidate` воспроизводит закреплённый downstream diff в отдельной detached worktree. Регрессионные тесты подтверждают точное tree SHA, обнаружение конфликтов, проверку ancestry и сохранность исходного checkout. Для обновления продуктового пакета потребуются build/runtime результаты конкретного кандидата.

В отдельной локальной копии также выполнен replay настоящего репозитория. Fork-коммит `f34d738cbd8e9e66981e93e13f19401c236b85ce` воспроизведён поверх той же базовой ревизии `f7fc2f2a08a3aa446baa23960710e630c5defd6e`. Получены `preparation = pass`, `main_guard = pass` и точное совпадение tree SHA `0995be6b99f242c42cb6b3b40a675685a9628835` с исходным fork. Кандидат сохранён для осмотра, его downstream diff находится в индексе. [Квитанция воспроизведения](../../.agent/runs/2026-11-06-foundation/candidate-rehearsal.json)

Общий статус кандидата равен `fail`, поскольку продуктовый код этой ревизии содержит платформу Warp. Выполненный replay относится к текущей базовой ревизии. Переходы между версиями очищенного приложения требуют отдельного прогона после реализации удаления.

## Дальнейшая реализация

1. Перенести `SerializedBlockListItem` из AI-модуля в терминальную persistence-область с сохранением сериализованной формы.
2. Освободить terminal snapshot и persistence от обращений к AI singleton-моделям.
3. Ввести собственные application ID, channel configuration и пути состояния для первого исполняемого кандидата.
4. Последовательно удалить закрытые платформенные подсистемы, включая их настройки, actions, зависимости, assets и фоновые службы.
5. Выполнить Windows GUI/ConPTY-сценарии и проверить реальный `Get-Location` в каждой восстановленной панели после обычного выхода, аварии и обновления.
6. Подтвердить воспроизведение очищенного форка на двух переходах между тремя последовательными ревизиями апстрима.

Подробные точки изменения и переносимые решения доноров записаны в [EXCISION.md](EXCISION.md). Сценарии первой поставки перечислены в [ACCEPTANCE.md](ACCEPTANCE.md), исполнимые проверки — в [TESTING.md](TESTING.md).

В отчётах GUI, ConPTY, TUI/OMP, реальное восстановление shell CWD, изоляция релизного EXE и процессная сетевая трасса имеют статус `NOT_RUN`. В текущем upstream `WARP_DATA_PROFILE` учитывается только в debug-сборках. Релизному кандидату требуется проверенный контракт собственных путей состояния.

`NOT_RUN` отмечает ещё не выполненную регрессионную приёмку конкретного пакета. GUI, ConPTY и терминальный движок наследуются из работающего Warp. Имеющиеся результаты позволяют начать удаление платформы, дальнейшие проверки выполняются по готовности изменённого поведения и пакета. Уточнённое задание Windows-only находится в `.agent/START.md`.
